## What this document is, and is not

It answers three questions for each of the seven services B5 adds or changes:

1. **Who attacks it, how, and what stops them?** — the abuse-case table.
   HP-5's twelve named topics are the minimum bar; the index in
   ["HP-5 topic coverage"](#hp-5-topic-coverage) shows where each is answered.
2. **Who owns each new piece of data?** — the data-ownership table: read,
   write, delete, what the subject sees, what the operator sees, and whether
   it is in a backup.
3. **When does it go away?** — the lifecycle table: the retention default,
   the behaviour under B4-9 erasure, B4-10 deletion markers and B4-11
   retention sweeps.

It is **not** an implementation plan (that is
[the B5 plan](../plans/b5-community-content-moderation-2026-09-04.md)), and
it is **not** a threat report on shipped code. Analysis that would name an
exploitable weakness in shipped code stays out of this repository
([docs/security.md](../security.md), "What stays private") and is counted,
not described, in ["The private half"](#the-private-half).

## How to read the tables

**"Tested at" has exactly two legal forms.** Either it cites a path that
exists at `cbebd37c` — a test file, or a source file whose own tests are
named — or it names the step that owes the test (`B5-1`…`B5-12`, `HP-5`,
`B7`, `B8`, `B9`). No cell is blank and none says "unknown". A row whose
control does not exist yet still carries the _today_ evidence where there is
any, so a reviewer can tell "unprotected" from "protected by something
weaker".

**"Control" is the control that exists at `cbebd37c`**, followed by what the
named step adds. "**None today**" means exactly that, and it is one of two
things: a service that does not exist, in which case the grep proving its
absence is in [the status table](#status-of-the-seven-services-at-cbebd37c);
or a service that exists and does not do this, in which case the row names the
file that would have to do it and does not.

**"Operator sees" means through a product surface** — an admin panel route,
an API, a broadcast. It is never a claim about the raw database. The
operator can read, search and delete anything in the SQLite file and in
`upload.storage_dir` by design
([trust-model.md](../trust-model.md), "What the operator can and cannot do");
that is true of every row here and is not repeated in every cell.

**"In a backup" means the scheduled or on-demand database backup**
(`Server/admin/handlers_backup.go`, `Server/db/admin_queries.go`), which is
`VACUUM INTO` of the SQLite file. **Uploaded files are not in it** — the
`upload.storage_dir` tree must be backed up separately or a restore loses
every attachment. Neither is `data/erasure/markers.sqlite`, which is
deliberately outside the file a restore overwrites (`Server/db/markers.go`).

**"B4-11 sweep" is narrower than "retention", and wider than "messages".**
The sweep _selects_ only out of `messages` (`retentionCandidates`,
`Server/db/retention.go`), but the transaction it runs reaches further: it
reverses mention counts on `read_states`, deletes the `attachments` rows of the
swept messages and unlinks their files, and purges the matching `events` rows
and ring-buffer frames (`Server/db/retention.go`, `Server/service/retention.go`).
So **"not swept" in a lifecycle row means "the sweep neither selects this class
nor reaches it through a swept message"** — which is exactly why S3-c and S3-d
say the opposite.

**Data-class numbering.** B4-0's inventory numbers classes 1–27 for data
that exists today. B5's new classes are numbered per service (`S1-a`,
`S1-b`, …) because none of them exists yet and renumbering B4-0's table from
a document that adds no rows to it would be churn. When a B5 step lands its
migration, its classes join `db.SubjectInventory` (`Server/db/inventory.go`)
and B4-0's table under the next free numbers — that is part of each step's
work, not this document's.

**Built by:** B5-6 (migration `046`), behind HP-5. **Register rows:** BG-13

## S2 — External content retrieval

The per-path inventory is [rich-content-inventory.md](rich-content-inventory.md).

**Built by:** B5-1 (`Server/safefetch`, **landed** `af473ff4`) and B5-5
(inventory, **landed**), both in front of HP-5; the desktop half is B7. **Register rows:** SEC-03 (P1, confirmed),
BG-19 (B5/B9). **Decisions:** 1 (phase split), 2 (per-fetch policy only), 3
(previews stay client-fetched).

The paths that fetch attacker-influenced content are **one live server path,
one dormant server path, and three renderer paths**. Since B5-1 the two server
paths share one policy; the three renderer paths share none, with each other or
with the server:

1. `Server/api/gif_handler.go` — the GIF proxy, and the only outbound content
   fetch the server actually performs. Upstream is the hard-coded `gifAPIBase`
   constant, so the URL is never attacker-chosen; only the search term is.
   Since B5-1 it fetches through a `safefetch.Fetcher` built at package scope
   (`gifFetcher`): `https` on port 443 only, **zero** redirects, a 10 s
   deadline, a 2 MiB ceiling on the wire **and** after inflation, a JSON
   content-type allowlist, and a concurrency cap of 8. The response is still
   re-encoded through a struct that acts as a field allowlist. The routes are
   mounted unconditionally and answer `503 GIF_DISABLED` with no key
   configured (`Server/api/router.go`).
2. `Server/plugin/host_http.go` — `(*Registry).HTTPDo`: an arbitrary
   plugin-supplied URL, any method, any body, an operator host allowlist that
   is empty by default. Since B5-1 it too fetches through `safefetch`, so its
   five redirect hops are each put through the whole destination check rather
   than only the host allowlist, and it gains the deadline, both byte
   ceilings, the content-type check and a process-wide concurrency cap of 8.
   **It still has no caller.** `grep -rn 'HTTPDo|host_http_request' Server
--include=*.go` finds only its own definition and comments, and
   `Server/plugin/sandbox_wazero.go` says "No host imports are wired into the
   runtime yet". So a plugin cannot reach it in any build — which is precisely
   why B5-1 adopting it now matters: wiring it up later is a small change, and
   a boundary absent at that moment is one that never gets applied.
3. `Client/src/components/message-list/embeds.ts` — `fetchOgMeta`, run in the
   **renderer** through `@tauri-apps/plugin-http`, on every message render.
   Its destination check (`isBlockedForPreview` → `isPrivateHost`) inspects
   the **hostname string**, not a resolved address.
4. `Client/src/components/message-list/media.ts` — an oEmbed `tauriFetch` on
   every YouTube render, with no destination check, no byte cap and no
   timeout.
5. `Client/src/components/message-list/attachments.ts` — `if (!isServerUrl(url))
return tauriFetch(url)` for external images, then `res.arrayBuffer()` with
   no byte cap. [trust-model.md](../trust-model.md) names all three renderer
   files, plus "the webview's own image loading", as C-09's subject; the first
   draft of this section named only the first, which is the error C-09 clause 1
   exists to prevent.

B5-1 moved the dialling out of both call sites, which was an inventory change
and not just a refactor — `TestEgressAllowIsLive` fails a listed file that
stops dialling. `Server/invariants/egress_sites.go` and
[diagnostics.md](diagnostics.md) now carry `safefetch/policy.go` and
`safefetch/fetch.go` in place of the two old rows, and the stale "route not
mounted" gate this document recorded went with them. The renderer paths are in
no inventory — nothing machine-checks them, which is C-09's whole point.

## S3 — Uploads, quotas and reserved headroom

**Built by:** B5-2 (migration `044`), in front of HP-5. **Register rows:**
SEC-04 (P1, confirmed; decision 12 re-tags it `B3/B5`). **Decisions:** 11
(counting point, defaults, one headroom constant), 12 (SEC-04 is B5's).

What exists today, all of it in `Server/api/upload_handler.go`,
`Server/storage/storage.go` and `Server/api/constants.go`:

- `POST /api/v1/uploads`, session-authenticated, **10 uploads per minute per
  user** (`auth.Key("upload", user.ID)`), a 100 MiB request-body ceiling and
  a 10 MiB multipart memory limit.
- A per-file ceiling of `upload.max_size_mb` (compiled default 100), enforced
  while writing plus a one-byte over-read probe, with the partial file
  removed on any failure after `os.Create`.
- Magic-byte type validation before the body is written
  (`storage.ValidateFileType`), filename sanitisation and a resolved-path
  containment check (`Server/storage/storage.go`).
- An orphan sweep on the 15-minute maintenance tick. Its predicate is
  `uploaded_at` older than an hour **and** (`message_id IS NULL` **or** the
  owning message is soft-deleted) **and not** an avatar
  (`Server/db/queries/sqlite/attachments.sql`); the clock runs from **upload**,
  not from unlinking, and the whole pass is skipped when no file storage is
  configured (`Server/internal/app/maintenance.go`).
- Free-space **signals**: a start-up banner that warns at 1 GiB and errors at
  256 MiB (`Server/internal/app/banner.go`), `/health` degraded below 256 MiB
  (`Server/api/router.go`), and `disk_free_mb` on the metrics surface
  (`Server/api/metrics_handler.go`).

What did not exist before B5-2, and does since migration `044`: a durable
per-user byte counter (`user_storage`, charged before every attachment or
avatar write by `UploadService.Reserve` in `Server/service/storage_quota.go`
and recounted from the rows on the maintenance tick), a reserved-headroom
floor that refuses an upload with `507` before the write, and one definition
of "low disk" — `server.min_free_disk_mb`, read by the banner, `/health` and
the upload path alike. Emoji are a **bounded exclusion** from the quota, not
from the floor: server-wide assets that change owner on erasure, gated on
MANAGE_SERVER and capped at `MaxEmojiCount` × `maxEmojiFileBytes`
(`Server/service/upload_quota_test.go`, `TestReserveHeadroom_EmojiIsBoundedAndFloorOnly`).

## S4 — NSFW labelling and acknowledgement

**Built by:** B5-7 (migration `047`), behind HP-5. **Register rows:** BG-18
(B5/B9). **Decisions:** 13 (server-side row, revocation, moderators
acknowledge too), 14 (exit condition 3 is met at the server only).

The label is **not** greenfield and the acknowledgement is **not** server-side.
`channels.nsfw` has existed since migration `025`, whose own header states the
contract: the server "stores it, ships it in `ready` and in the
channel_create/channel_update broadcasts, and audits the edit — it
deliberately imposes NO content behaviour of its own: no filtering, no age
check, no restriction on who may read or post". Today's gate is entirely in
the desktop client: `Client/src/lib/nsfw-gate.ts` remembers an
acknowledgement in **sessionStorage**, keyed by channel and server host, and
its own doc comment calls it "a courtesy prompt, not a security control — a
determined reader clears the key, and the messages were never withheld by the
server anyway."

That sentence is the whole of S4's abuse surface. B5-7 replaces it with a
row.

## S5 — Report intake, the queue and evidence snapshots

**Built by:** B5-8 (migration `048`), behind HP-5. **Register rows:** BG-14
(B5/B9). **Decisions:** 7 (evidence content erased, outcome row survives as
an unlinkable B4-10-style audit row).

Wholly greenfield: no table, no route, no service, no message type. Every row
below is therefore a **requirement on B5-8**, not a description. The two
things that already exist and constrain the design are the audit log's
unlinking mechanics (migrations `038` and `041`, `Server/db/erasure.go`) and
the fact that the audit log has no delete path at all — production code
inserts and, on erasure, unlinks; nothing prunes it.

**A report names two people.** That is the shape migration `041` was added
for: "an audit row names two principals, so an erased actor needs a token of
its own rather than sharing the subject's". A report has a reporter and a
subject, and either can erase; B5-8 needs the two-token pattern, not one.

## S7 — Web Push subscriptions and dispatch

**Built by:** B5-4 (storage, migration `045`, in front of HP-5) and B5-11
(dispatch, behind it). **Register rows:** BG-05 (B5/B8). **Decisions:** 9
(dispatch off by default and inventoried in `egress-sites`).

Greenfield on the server: `grep -ril 'vapid|push_subscription' Server protocol
Client/src` returns nothing, and `grep -in push Server/config/config.go`
returns nothing. What exists is a **different thing that is easy to confuse
with it**: the desktop client composes and fires its own local notification
from a message it already received (`Client/src/lib/notifications.ts`,
`fireDesktopNotification`), through the Tauri notification capability
(`Client/src-tauri/capabilities/default.json`). That path sends nothing off
the machine. Its body today is the message content, control-stripped and
truncated to 100 characters — which is the baseline decision 9's
generic-content default deliberately departs from, because a Web Push payload
transits a third party.

**S7 is the only B5 service that adds an outbound network path.** That makes
`Server/invariants/egress_sites.go` a hard dependency: B5-11 adds a `config`
row whose destination is "the push service named in each stored subscription
endpoint", and `TestNoAutomaticTelemetry_Capture` must stay green on compiled
defaults — which it does, because the default is off (decision 9).
[diagnostics.md](diagnostics.md)'s egress table is the human-readable half and
gains the same row.

## What B5 does not defend against

Written so HP-5 reviews an honest boundary rather than an implied one. None
of these is an oversight; each is a scope line, a trade-off taken knowingly,
or a property the architecture cannot have.

1. **The operator.** They can read, search and delete anything on the server,
   and with shell access they can edit the binary, the database or the
   marker file. Every control here is a control on _users_, not on the person
   running the machine. [trust-model.md](../trust-model.md) is the disclosure;
   nothing in B5 narrows it, and reports, notes and evidence snapshots widen
   the set of sensitive material the operator holds.
2. **Block bypass through an existing group DM.** `requireDMNotBlocked`
   returns early for group channels; blocks are enforced pairwise at group
   creation only. Someone blocked _after_ the group existed can still send
   into it. Decision 4 keeps group-DM invitations out of beta scope, so B5
   does not change this.
3. **Anything a person has already been shown.** A recipient who accepted a
   request, a moderator who read an evidence snapshot, a reader who
   acknowledged a labelled channel — none of it can be un-seen, and
   screenshots are outside every model here.
4. **The viewer's address, to a host someone else linked.** Decision 3 keeps
   previews client-fetched, which exposes the _viewer's_ address rather than
   the operator's. C-09's broker (B7) bounds it; B5 does not.
5. **Delivery metadata to a push service**, once an operator turns dispatch
   on. The service learns that an endpoint was pushed and when. Generic
   content keeps the _what_ out; the _when_ is inherent to Web Push.
6. **A client that ignores the label.** The NSFW flag is metadata on the
   wire; B5-7 makes the server withhold content until an acknowledgement row
   exists, which is a real control, but the label's _meaning_ is still
   advisory and the server knows nobody's age.
7. **Sybil registration at scale.** Registration modes (open, invite,
   approval) are the whole answer; there is no CAPTCHA, no proof of work and
   no email verification — OwnCord works without SMTP by design.
8. **Reputation across servers.** Each server is an island: no shared ban
   lists, no federated abuse signals, no cross-server identity. A blocked
   user simply joins a different OwnCord.
9. **Automated content classification.** Roadmap workstream 10 keeps
   automation optional and post-beta; B5 ships human moderation and audit,
   and nothing that scans or scores content.
10. **An evidence snapshot outliving the author's own deletion.** Decision 7
    settles _erasure_. Ordinary message deletion by the author does not reach
    a snapshot taken earlier; B5-8 owes a test that pins whichever behaviour
    ships, and this is the trade-off that motivates it.
11. **A shared device inheriting an NSFW acknowledgement.** Decision 13 puts
    the row server-side so a new device does not re-prompt; the cost is that
    a second person on the same account does not either.
12. **Aggregate cross-caller byte budgets, and byte-weighted cache eviction.**
    Decision 2 defers both to B7. B5-1 shipped the per-fetch policy and two
    concurrency gates — per `Fetcher` and process-wide — but there is no
    cross-caller byte ceiling, and `safefetch` fills no cache.
13. **The desktop renderer's fetch policy.** C-09 clauses 1, 7 and 8 — the
    native broker owning renderer fetches, returning a typed minimum, and
    narrowing the `https://*` capability — are B7's. Until then the renderer's
    remote fetches are governed by the capability scope and the per-call-site
    checks in `Client/src/components/message-list/`.
14. **Content remanence after a sweep.** The account erasure runs its
    transaction under `PRAGMA secure_delete = ON` and truncates the WAL
    afterwards; the retention sweep uses the ordinary writer and does not
    ([data-lifecycle.md](data-lifecycle.md), class 25: "other writes keep the
    default"). Swept message text — and any B5 class removed the same way —
    can persist in the database file's free pages until those pages are
    reused.
15. **A restore that loses attachments.** The database backup is
    `VACUUM INTO` of the SQLite file; `upload.storage_dir` is not in it. Every
    evidence snapshot and attachment row that references a file assumes the
    operator backed that tree up separately.
16. **A block check that fails open.** `requireDMNotBlocked` treats a
    `GetDMRecipient` error, and a DM with no other participant, as "not
    blocked" (`Server/service/message_perms.go`, under a documented
    `//nolint:nilerr`). It is the posture `checkSendPermission` already
    takes, and B5 does not change it; a database error during a send
    therefore delivers rather than refuses.
17. **A copy of every image on every viewer's disk.** The desktop client
    stores fetched attachment bytes in IndexedDB (`owncord-image-cache`,
    `Client/src/components/message-list/attachments.ts`) and nothing in the
    app evicts them — `clearAttachmentCaches` does not. Server-side erasure
    and retention remove the file from `upload.storage_dir`; the copies stay.
    Data class **S2-f**.
18. **The client halves of exit conditions 2 and 3.** Decision 14 states
    both are met at the server only, with B7 and B9 owing the rest. This
    document covers server behaviour except where a row says otherwise.

5. **Every migration B5 adds is documented here.** Any `Server/migrations/*.sql`
   numbered `044` or above must be named in this file, and any migration this
   file names below `044` must exist. That is the class-list coupling B5-0's
   acceptance asks for: when B5-2 lands `044`, this document has to grow a row
   or the gate goes red.

**What the gate does not check, on purpose.** It verifies shape and existence:
that a section is present, that a table's columns are named as expected, that a
cell is populated, that a cited path resolves, that a B5 migration is
documented. It does not read a cited test and cannot tell that the test proves
the claim in the row beside it. Several rows in this document say "no test
exists" precisely because a human went and looked; keeping that true is a
reviewer's job, and HP-5's.

Run it with `-count=1`. This file lives outside the `Server` module, so Go's
test cache does not record it as an input and a plain `go test ./...` answers
a doc-only edit from cache. `scripts/run.mjs` and `.github/workflows/ci.yml`
each give it its own `-count=1` step for that reason, exactly as they do for
`TestServerBoundariesDocIsCurrent`.
