# Rich-content inventory

This document is BPR-061's "existing provider/feature inventory" prerequisite
and the artefact B7's native fetch broker implements against. It is a
per-path map of every place OwnCord fetches content that was not chosen by
the operator: who starts the fetch, which side of the client/server line
performs it, what host class it can reach, and exactly what bounds — address,
redirect, byte, time, type, concurrency, cache — apply today. Where a bound
does not exist, the cell says so and names the phase that owes it, never
`unknown`. Measured at `123b07d8`.

Two rules this document exists to keep visible. First, **link previews stay
client-fetched** (plan decision 3): a server-side unfurl proxy would make the
server dial attacker-chosen hosts on every message containing a link, which
reverses the "your server does not phone home" property `egress-sites`
enforces; the cost of that choice is that the _viewer's_ renderer, not the
operator's server, is who a hostile link deanonymises, and closing that gap is
C-09's job, owed to B7, not to the server. Second, **the server owns exactly
one outbound content path that fetches attacker-influenced hosts**: the GIF
proxy (`Server/api/gif_handler.go`), routed through `Server/safefetch` since
B5-1. The plugin `http` capability (`Server/plugin/host_http.go`) shares the
same `safefetch` boundary but is not "content" in the sense this inventory
otherwise tracks — it is an operator-configured integration point with no
caller wired into any build today — and two operator-triggered binary
downloaders exist beside it for completeness. Every other row below is a
**desktop renderer** fetch, made directly from TypeScript through
`@tauri-apps/plugin-http` or the webview's own image loading, each with its
own destination policy (or none), which is exactly the "not centralised at
the native boundary" finding `docs/trust-model.md`'s C-09 contract exists to
close in B7.

**The link-preview destination check, in detail** (the note the "Link
preview" row above owes rather than a row of its own). `isBlockedForPreview`
(`Client/src/components/message-list/embeds.ts:132-142`) calls `isPrivateHost`
(`:94-130`), which inspects the **hostname string** — never a resolved
address — against a hand-written table of loopback, RFC 1918, link-local,
CGNAT, multicast and a handful of documentation/benchmarking ranges, plus a
short list of IPv6 forms (`:96-111`); `parseIPv4Literal` (`:79-92`) recognises
only a plain dotted-quad literal, so a hostname that resolves to a private
address is not caught at all — exactly the gap `docs/trust-model.md`'s C-09
clause 3 discloses and assigns to B7's native broker (which resolves before
classifying, the way `Server/safefetch` already does on the server side). The
connected OwnCord server's own host is exempted (`isTrustedServerUrl`), since
it is already trusted.

**The GIF proxy's exact policy**, for the row above, as the literal
`Server/safefetch.Policy` it is built from (`Server/api/gif_handler.go:66-75`):

```
Schemes: ["https"], Ports: [443], ContentTypes: ["application/json", "text/plain"],
MaxRedirects: 0, Deadline: 10s, MaxBytes: 2 MiB, MaxDecompressedBytes: 2 MiB, MaxConcurrent: 8
```

`text/plain` rides along in the allowlist for a recorded reason, not a guess:
the handler's own comment (`gif_handler.go:63-65`) explains that
`http.DetectContentType` reports `text/plain` for every textual format
including JSON, so the pairing is required for a legitimate JSON response to
pass sniffing at all — it does not widen what is accepted, because an HTML
error page served with either declared type is still refused by the sniffed
half of the check (`TestGIFWrongContentTypeBecomesBadGateway`,
`TestGIFMalformedUpstreamBecomesBadGateway`). B5-5 read this and made no
change, per its own instruction not to alter behaviour on a guess.

**B5-5's result-URL hygiene filter**, added to the row above: every
`gifResult` URL field forwarded to the client (`media_formats.tinygif.url`,
`media_formats.gif.url`) must parse, be `https`, carry a non-empty host and
carry no embedded userinfo, or that individual result is dropped from the
response — not the whole response (`validGIFResultURL`,
`Server/api/gif_handler.go`; `TestGIFResultURLsAreHTTPSWithoutCredentials`).
This is a second gate on values _inside_ an already-bounded, already
type-checked body: `safefetch` validates the envelope the upstream sent, not
the URLs nested inside its JSON, and those nested URLs are exactly what the
"GIF render on the client" row above fetches next, directly and unproxied.

## What changed in B5-5, and what did not

**Changed.** (1) This document — the inventory did not exist before. (2) The
GIF proxy gained a result-URL hygiene filter: a malformed, non-`https`, or
credential-carrying URL inside an upstream result is dropped from the
response rather than forwarded (`validGIFResultURL`,
`TestGIFResultURLsAreHTTPSWithoutCredentials`). (3) A new test,
`TestGIFOfflineUpstreamIsBadGatewayWithoutLeak`, pins the already-correct
behaviour for a non-resolving upstream host: `502 BAD_GATEWAY`, no upstream
host or resolver text or API key in the body, answered well inside the 10 s
deadline. (4) S-03: a new test, `TestS03_GroupDMNameCountsRunesNotBytes`
(`Server/service/dm_test.go`), pins that the group-DM rename path
(`RenameGroupDM` → `cleanTextBounded` → `MaxGroupDMNameLen`) counts runes, not
bytes, the same way the admin channel writer already does
(`TestChannelMeta_NameCountsRunesNotBytes`); the cap-equality test
(`TestChannelMeta_SharesTheGroupDMNameCap`) already existed and needed no
addition.

**Not changed.** (1) No client code — every renderer-side row above was read,
not edited; B7 owns that work. (2) The GIF content-type allowlist
(`application/json`, `text/plain`) — its reason is recorded in the handler's
own comment and is left as-is (see above). (3) No migration, no configuration
key, no protocol change, and no `findings-ledger` row — none was called for.
(4) S-03's contract itself (`cleanChannelMeta`, `cleanTextBounded`,
`MaxGroupDMNameLen`) was implemented in B3-8 and verified here, not rebuilt.
