# CI cost, 2026-10

**Date:** 2026-10-21
**Window:** every completed workflow run created from 2026-09-21 to 2026-10-20
(UTC), all events, every attempt.
**Audited tree:** `dev` at `7bd9f7b`.
**Scope:** ARCH-047. How many runner minutes CI spends, where they go, and
whether the required Windows native E2E job, with its 100-minute timeout,
should move off pull requests.

## 1. Method

`scripts/ci-cost-report.mjs` reads the runs a day at a time from the GitHub
REST API, then every job of every attempt, and sums each job's wall time from
`started_at` to `completed_at`. Skipped jobs count nothing. Re-run it with:

```
GITHUB_TOKEN=... node scripts/ci-cost-report.mjs --days 30 --cache .ci-cost-cache
```

It needs about 11,000 API calls for 30 days, close to the hourly limit, so it
waits for the limit to reset and `--cache` keeps the jobs it already read.

**The repository is public, so GitHub does not bill these minutes.** The
"billed-equivalent" column applies private-repository rules (rounded up per
job, Windows ×2) only to make the numbers comparable with the 2026-09-20
estimate. The real cost is the plan's cap of 20 concurrent jobs, which every
lane's PR run queues behind, and the wall time a PR waits.

## 4. The Windows native E2E

- 2,921 runs. p50 17.1 min, p90 20.2, p99 25.3, max 62.9. Only 3 runs took
  over 30 minutes, 2 over 50 and 1 over 60. **No run came near the 100-minute
  timeout.**
- It failed 116 times (4.0%), about the same rate as the real-media job (3.9%)
  and below the server legs (5.5–5.7%).
- It is the most expensive single job, 14.9% of all job-minutes, because it
  runs on almost every PR: any server or client change selects it
  (`scripts/ci-select.mjs`, `native`). Each run holds one of the 20 job slots
  for about 17 minutes.
- Its p50 of 17.1 minutes is under the CI run's p50 of 23.8, so on a typical
  run other jobs finish later. This report does not compute the critical path
  run by run.

**Changed in this PR:** the job's `timeout-minutes` goes from 100 to 70. That
covers the slowest run in the window with 7 minutes to spare and frees a
hung run's slot half an hour sooner.

**Not changed: moving it to dev pushes only**, which ARCH-047 suggested. It
would save about 40,000 job-minutes a month, but it is the only PR check that
builds the real Tauri app and installs it. A break would be found after merge,
on `dev`, by every lane at once. It is also a required check on `dev`, so the
move needs a branch-protection change. With the minutes free and the job off
the critical path, the trade is not worth it. Re-measure if the plan's
concurrency becomes the bottleneck (see section 6).

## 5. Nightly Test Depth fails every night

21 of 29 nightly runs failed. Every scheduled run since 2026-10-17 ran the
**old six-shard mutation matrix**, with each shard cancelled at 90 minutes.
Scheduled workflows run the copy of the workflow file on the default branch,
`main`, and the 31-shard split only exists on `dev`. The manual runs from `dev`
on 2026-10-16 and 2026-10-17 passed with the new split, each shard in 60–82
minutes.

It fixes itself at the next release, when `dev` merges into `main`. Until then
the nightly mutation result is red for a reason that has nothing to do with the
code. B11 asks for trustworthy nightlies, so this matters before the beta ends.

## 6. Recommendations

1. **Keep the Windows native E2E on pull requests** (section 4). Done: the
   timeout is now 70 minutes.
2. **Release `dev` to `main` before trusting the nightly mutation numbers**
   (section 5). Nothing to fix in the workflow itself.
3. **The 20-job concurrency cap is the real budget.** One PR run is about 14
   jobs, so two lanes pushing at once already queue. If the owner moves to a
   paid plan (40 jobs), re-run the script and compare the wall p50 and p90.
4. **Re-run this report monthly** with `scripts/ci-cost-report.mjs`. It takes
   about an hour because of the API limit.
