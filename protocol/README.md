# `protocol/`

This folder holds the WebSocket contract between the server and the client.
Read it before you add or change a message type, or touch the wire fixtures.

It lives at the repository root because neither side owns it. `schema.json` is
the single source of truth for the message-type constants that **both** the Go
server and the TypeScript client compile against.

| File                | Role                                                                                   |
| ------------------- | -------------------------------------------------------------------------------------- |
| `schema.json`       | Source of truth. Every wire message type, in both directions, and the closed `enums`   |
| `fixtures/epoch-1/` | Frozen wire transcripts for protocol epoch 1. Regenerated by a test, never hand-edited |

Two files are generated from `schema.json`. Never edit them by hand:

- `Server/ws/message_types.go`
- `Client/src/lib/protocolTypes.ts`

## Changing the protocol

`schema.json` also sets `protocol_epoch`. That is the one version number the
auth handshake agrees on. Additive changes stay within an epoch. A breaking
change bumps it. The rules, and what a bump requires, are in
`docs/protocol.md` under _Compatibility_.

To change the protocol:

1. Edit `schema.json`.
2. Regenerate both generated files with one command from the repository root:

   ```bash
   npm run generate
   ```

   This also regenerates the sqlc query layer and the generated doc blocks.
   To regenerate only the protocol constants, run `make protocol-generate` or
   `go run ./cmd/genprotocol` from `Server/`. The generator is a Go program, so
   it lives where the Go toolchain already runs.

Four checks catch a mistake, so there is nothing extra to run:

- `.githooks/pre-commit`, `make protocol-verify` in CI, and
  `npm run check:server` each reject a stale regeneration.
- `Server/ws/protocol_contract_test.go` checks the schema against the
  constants on its own.

## Fixtures

`fixtures/epoch-1/` holds one JSON file per journey (fresh connect, chat send,
voice join, and so on).

- **Frames are listed per connection.** Within a file, each connection has its
  own list of frames, in order. Frames on different connections are not
  related. The order between connections depends on timing and is not part of
  the contract.
- **Changing values are replaced by placeholders.** Ids, sequence numbers,
  timestamps, tokens and user ids become typed placeholders such as
  `"<id:number>"`. So a refactor that keeps the wire shape leaves the file
  unchanged. A renamed, added or removed key, or a type change, shows up as a
  diff.

**Who checks them.**

- `TestEpoch1Fixtures` in `Server/ws` runs the real server in-process and
  compares its output with these files. It runs under `go test ./...`, so
  `npm run check:server` and the Server Build & Test CI check already cover it.
- The client replays the same files through its dispatcher in
  `Client/tests/contract/protocol-fixtures.test.ts`. So a regenerated fixture
  must also pass `npm run test:contract` from `Client/`
  (`npm run check:client` covers it).

**To regenerate,** run this from `Server/`, then read the diff frame by frame
before you commit it:

```bash
go test ./ws -run TestEpoch1Fixtures -update
```

### When a fixture may change

**A fixture's shape may change only on purpose. An epoch bump is for what older
clients cannot process.**

- **A change an older client can ignore** is allowed within an epoch. Examples:
  a new key, or a new optional field. Regenerate `fixtures/epoch-<n>/` in the
  same PR, read the diff frame by frame, and document the addition in
  `docs/protocol.md`.
- **A change an older client cannot process** needs a new
  `fixtures/epoch-<n+1>/` folder. Keep the old one as the record of what earlier
  clients speak. Examples: a key removed, renamed or retyped; a frame dropped;
  or the order of frames on one connection changed.
- A diff of that second kind in a change that does not bump the epoch is a
  protocol break. Revert it; do not accept it as a refactor.
- Epoch negotiation itself was an additive change, and stayed on epoch 1.

**A seeded default value is not a protocol change.** The fixtures record real
values wherever they are predictable. Examples: role permission masks and
colours, `motd`, `server_name`, a channel's `voice_max_video`, and the
`voice_config` preset. So a migration that changes a default mask moves a
fixture without touching the wire. Regenerate in the same PR and read the diff
frame by frame.

Do not hide those values behind placeholders. A placeholder over a mask, or
over an enum such as `voice_config.threshold_mode`, would hide exactly the
drift these files exist to catch.

**A fixed vocabulary is shape, not a seeded value.** This means a value from a
fixed list that the client switches on: `threshold_mode`, `quality`, `status`,
`replay_source`, a channel `type`. Renaming or dropping a member of such a list
is a protocol change, even though only a value moved.
